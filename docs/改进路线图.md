# 屿宁学习通助手 · 改进路线图

> 编制依据：全量源码通读（37 文件 / 7,328 行）+ 三轮评审迭代
> 评估维度：**收益**（用户可感知程度）× **成本**（改动量）× **风险**（引入回归或封号风险）
> 约束前提：保持"不伪造上报"的架构原则、保持纯 JS 无构建步骤、单人维护

---

## 0. 评估框架：先排除三类错误答案

在列具体建议前，先明确什么**不该**做，因为它们会浪费大量精力却适得其反：

| 不建议 | 理由 |
|---|---|
| 继续提高倍速（3x/4x） | 学习通上报的是播放器 `currentTime` 增量。2x 已在"人类可完成"的合理边界内，更高倍速会显著提高风控命中率。**收益为负。** |
| 直接调用上报接口补进度 | 违背项目唯一的核心自我约束（§1.2），一次性把"UI 自动化"降级为"协议伪造"，维护成本与封号风险同时暴涨。 |
| 引入构建工具 / 框架 | 当前零依赖、改完即加载，是单人维护的巨大优势。为"工程规范"引入 Vite/TS/webpack，收益远小于常年维护成本。 |
| 强行兼容 `pan-yz.chaoxing.com` 跨域 iframe | 需注入 `all_frames` + 跨域消息中转，改动面覆盖 manifest、doc、dom、main 四个模块，而该场景罕见。**投入产出比最差。** |
| 悲观化所有流程（任何不确定都报错重试） | v0.5.1 的 §6.1 修复已证明：诚实失败会带来重试噪声。继续扩大"如实报错"的范围，会让日志不可读。需要的是**分级判定**，不是全盘悲观。 |

## 1. 第一梯队：决定"能不能跑完"

这一梯队直接决定用户在合上电脑后，任务是否真的能自动完成。

### 1.1 【强烈推荐】自动处理平台弹窗，而不是停下来等用户

- **现状**：`player/index.js:268-273` 一旦 `detectBlockers()` 命中（`core.js:175-178` 的五类遮挡），就 `v.pause()` 并向面板发 `BLOCKED`（`runner.js:128`），然后**整个任务停住等人工处理**。
- **问题**：超星在长时间播放后常弹「是否继续观看」这类**纯确认框**（`.layui-layer`，带"继续"按钮）。当前实现把它和「任务点已达上限」这种**需要用户决策**的弹窗混为一谈，导致本来能自动跑完的任务断在最后一步。
- **改进**：把 `detectBlockers()` 的返回值从"有无遮挡"升级为**三分类**：

  | 类型 | 判定依据 | 处理 |
  |---|---|---|
  | `confirmable` | 弹窗内存在文本匹配 `/继续观看|继续学习|确定|继续/` 的按钮 | **自动点击，继续播放** |
  | `need-user` | `.ans-job-limit-tip`、`.ans-job-limit`（任务点上限）、验证码 | 暂停 + 通知（维持现状） |
  | `unknown` | 其他遮挡 | 暂停 + 通知，但记录选择器供后续分类 |

- **收益**：极高 —— 直接减少"跑到 90% 卡住"的失败场景。
- **成本**：约 30 行，集中在 `core.js` 的 `detectBlockers()` 与 `player/index.js` 的 blocker 分支。
- **风险**：低。自动点击限制在白名单文本内，且点击后仍走 `canSafelyRecover()` 复核。

### 1.2 【强烈推荐】运行态持久化，支持关闭侧边栏后续跑

- **现状**：调度状态全在**内存**里 —— `SP.state.pendingResume`（`captcha.js:177`）、`SP.state.runningSectionId`、`globalRunId`（`task.js:12`）。侧边栏一关，这些全部丢失，正在跑的流程失去锚点。
- **问题**：侧边栏被误关 / 浏览器崩溃 / 扩展重载，都会让"正在进行的刷课"变成僵尸状态：content 侧还在播，面板侧已无法接管。
- **改进**：
  - 把 `runningTabId` / `runningSectionId` / `pendingResume` / 当前节的 `handledJobs` 快照写入 `chrome.storage.session`（MV3 内存态，扩展重载即清空，无持久化污染）
  - 侧边栏 `load` 时读取，若发现存在活跃会话，提示"检测到未完成的任务，是否继续？"
  - background 的 `TAB_UPDATED` 分支已有 `pendingResume` 恢复逻辑（`sidepanel.js:248-285`），改造为从 storage 读即可复用
- **收益**：高。把"意外关闭 = 全部重来"变成"关闭 = 可恢复"。
- **成本**：中等，约 60-80 行。
- **风险**：中。需注意与 `globalRunId` 的语义配合 —— 恢复时应递增 runId 让旧流程退出，与现有 `force: true` 路径一致。

### 1.3 【推荐】文档任务：从"盲滚动"升级为"有依据的滚动"

- **现状**（`doc.js:28-80`、`142-209`）：
  - `scrollOnce` 每轮遍历**全部** `div/section/article/main/ul/ol` 并逐个调 `getComputedStyle`（强制样式计算）
  - 稳定阶段固定跑满 5 轮 × 300ms，即使页面毫无变化
  - 无法判断"滚动是否真的推进了阅读进度"
- **改进**（三小步，可独立实施）：
  1. **候选容器缓存**：首轮扫描后把命中"可滚动"的元素缓存起来，后续轮次只操作缓存，避免每轮全量 `getComputedStyle`
  2. **无变化即退出**：`computeSig()` 已有（`doc.js:97`），把"连续 2 次不变"的阈值用于**提前判定"这是静态图，滚动无意义"**并跳出，而不是空转满 5 轮
  3. **优先使用阅读器自身的进度控件**：`#viewerContainer` / `.pdfViewer` 这类阅读器通常有页码输入框或进度条。直接设 `scrollTop = scrollHeight` 是"假滚动"，而翻页控件的状态变化才是平台真正监听的
- **收益**：中高。兼顾速度（少空转）与成功率（真实推进）。
- **成本**：低到中，约 40 行。
- **风险**：低。

### 1.4 【推荐】视频失败降级，不阻塞整节

- **现状**：`runner.js:99-104` 播放失败直接 `return false`，任务点进 `failedJobs` 进入下一 pass 重试；若某视频源永久损坏，会在"节级 3 × pass 2 × 全局 5 轮 × 最终 2 轮"框架内被反复重试。
- **改进**：
  - 记录同一任务点的**连续失败次数**，超过阈值（如 4 次）后标记为 `permanently-failed`
  - 该标记写入本节的进度缓存（复用 `section/core.js:28 markProgressDone` 的存储，但用独立 key），使其不再进入重试队列
  - 在面板的"待处理"区列出，让用户知道"这一个任务点需要手动处理"，而不是笼统的"本节未完成"
- **收益**：中。把"无意义重试拖长整节时间"变成"快速跳过 + 明确告知"。
- **成本**：低，约 25 行。
- **风险**：低。

## 2. 第二梯队：决定"好不好用"

### 2.1 【强烈推荐】面板增加"全局进度 + 预计完成时间"

- **现状**：`catalog-stat` 只显示"40 节 · 未完成 12"，任务点区显示"8 个 · 未完成 3"。**用户无法回答"还要多久"。**
- **改进**：
  - 顶部总进度条：已完成节 / 总节数
  - **ETA 必须分两条路算，因为两类任务的可预测性差一个量级**：

    | 任务类型 | 可预测性 | 算法 |
    |---|---|---|
    | 视频 | **高** —— `duration` 在播放前即可拿到 | `Σ(剩余视频 duration) ÷ rate`，精确 |
    | 文档 | **低** —— 10 页 PPT 约 15 秒，200 页 PDF 可能 2 分钟以上，交互动画类更不确定 | 首轮不预估；**记录实测耗时**，从第二次起用**同类的历史平均耗时**参与计算 |

  - 每节完成后用实测耗时回填，越跑越准（视频侧天然准确，主要是校准文档侧）
- **关键设计原则：宁可估高，不要估低。**
  - 估高 → 实际提前完成，用户获得正向意外；
  - **估低 → 用户盯着一个早就该结束的进度条，信任受损最快**。
  - 因此当文档侧尚未积累到足够样本时，**不要假装 ETA 是准确的**，而应改变**标签文案**：
    - 已校准：`预计剩余 32 分钟`
    - 未校准：`至少剩余 18 分钟（不含文档任务）`
  - **反对"把文档任务排除出 ETA"的做法**（评审建议的简化方案）：那会得到一个**系统性低估**的数值，恰好落在最伤信任的一侧。要么用历史均值参与计算，要么按上面的方式**显式标注为下限**，不能把它当完整 ETA 呈现。
- **收益**：极高 —— 这是长任务工具最核心的体验指标。
- **成本**：低到中，约 60 行（`task.js` 累计耗时 + 历史均值缓存 + `render` 呈现）。
- **风险**：低。

### 2.2 【推荐】把"需要你处理"的事件从日志里拎出来

- **现状**：验证码、登录过期、弹窗阻挡全部混在 `#log` 的滚动文本流里（`modules/utils.js:36`）。
- **问题**：用户去倒杯水回来，需要在一屏日志里找"是不是需要我做什么"。
- **改进**：在 `#log-card` 上方固定一个**待处理区域**：
  - 有阻塞事件时高亮显示（"⚠ 检测到验证码，正在自动识别（第 2/3 次）"）
  - 需人工介入时给出**具体动作**（"请完成验证码后点继续" / "请在某节手动播放该视频"）
  - 事件解决后自动消失
- **收益**：高。这是"半自动工具"的信任基础。
- **成本**：低到中，约 60 行（HTML 区块 + 事件订阅）。

### 2.3 【推荐】答题结果可复核、可纠正

- **现状**：`oneClickAnswer()` 填完即结束。`showQuizDetailModal()`（`modules/quiz.js:136`）能看题干和 AI 答案，但**看不到页面上实际选中的是哪些选项**。
- **改进**：
  - 详情弹窗同时显示「AI 答案」与「页面实际选中」（内容侧 `isOptionSelected` 已有，`quiz.js:14`，补一路回传即可）
  - 二者不一致的行高亮 —— 这既是纠错入口，也是**验证填入逻辑是否可靠**的直观反馈
  - 低置信度（`confidence < 0.6`）行加标记
  - 支持单题重答
- **收益**：高。当前用户对"AI 填得对不对"是完全不可见的。
- **成本**：中，约 80 行。
- **风险**：低。

### 2.4 【推荐】更新首次使用引导

- **现状**：只有"睡眠标签页"引导（`guide.js`）。而真正导致新手失败的三件事都没引导：API Key 未配置（只有 banner 一行字）、自动播放被浏览器拦截、验证码功能需要 MoMi 视觉模型。
- **改进**：扩展 `guide.js` 的分步引导，或在 `settings.js` 里加"自检"按钮：逐项检查 API Key 有效性、chaoxing 权限、当前页是否课程页，输出一份"可用性报告"。
- **收益**：中高（降低首次失败率）。
- **成本**：低，约 40 行。
- **风险**：低。

## 3. 第三梯队：决定"长期能不能维护"

### 3.1 【强烈推荐】选择器集中化 —— 应对超星改版的唯一有效手段

- **现状**：平台相关选择器**散落在 12 个文件里**，例如：
  - `.posCatalog_select` / `.icon_Completed`（`catalog.js:9-15`）
  - `.ans-job-icon` / `.ans-job-finished` / `.ans-attach-ct`（`jobs.js:11-43`）
  - `#iframe` / `#prev_tab .prev_ul > li` / `video#video`（`dom.js:7-66`）
  - `.answerBg` / `.singleQuesId` / `.completeBtn`（`quiz.js`）
  - `#viewerContainer` / `.pdfViewer`（`doc.js:62-66`）
  - 弹窗五类（`core.js:175-178`）
- **问题**：超星一次改版，需要翻 12 个文件找散落的字符串，极易漏改。这是此类项目**最主要的死因**。
- **改进**：新增 `content/selectors.js`（挂 `CXH.SEL`），把全部平台选择器收敛为常量对象，各模块引用。**同时带来第二个好处**：可以写选择器健康检查（见 3.2）。
- **收益**：极高（长期）。
- **成本**：中（纯机械替换，但涉及 12 个文件）。
- **风险**：低（无逻辑变更），但需要配合一次完整的回归测试。

### 3.2 【强烈推荐】选择器健康检查 + 一键诊断包

- **思路**：启动 / 每次 `SCAN_CATALOG` 时，校验一组"关键选择器"是否命中。任一关键选择器连续 N 次未命中，就在面板显式报警：**"检测到学习通页面结构可能已更新，扩展的 X 项功能可能失效"**。
- **配套**：一键导出**诊断包**（版本号、当前 URL、各关键选择器命中情况、`SCAN_CATALOG` 结果、最近 200 行日志）。
- **为什么价值高**：当前所有失败都表现为"没反应"或"卡住"，用户无法区分是**超星改版**、**登录过期**、还是**自己的配置问题**。这个功能把"玄学故障"变成"可读报告"，同时极大降低远程排障成本（你现在只能靠用户截图 Console）。
- **成本**：中，约 80 行。
- **风险**：低。

### 3.3 【推荐】给纯函数补一个零依赖测试脚本

- **现状**：项目**完全没有测试**。而回归风险最高的恰恰是几个纯函数：
  - `ai.js:142 extractCaptchaCode` —— 8 层提取策略 + 34 词黑名单，分支密集
  - `ai.js:79 parseAnswers` —— JSON / 逐行双通道
  - `section/core.js:44 jobKey` —— 三级降级
  - `jobs.js:72 classifyType` / `finder.js:11 classifyTypeSimple` —— 两者已有分歧
  - `quiz.js:44 normalize` / `49 inferType`
- **改进**：加一个 `test/run.js`，用 Node 内置 `assert` 直接跑，**零依赖、零构建**，可由一个 `check.ps1` 一并调用。
- **收益**：中高。尤其 `extractCaptchaCode` 一旦改动，没有测试就只能靠线上试错。
- **成本**：低到中。
- **风险**：无（纯新增）。

### 3.4 【推荐】加一个 `check.ps1` 质量门

**这是本次会话最直接的教训沉淀** —— 本次暴露的三类问题，全部可以被一个本地脚本拦住：

| 本次实际故障 | 能否被拦住 |
|---|---|
| `_stats.txt` 导致扩展无法加载 | ✅ 全树扫 `_` 前缀 |
| PowerShell 捕获 `git diff` 中文乱码（易误判为文件损坏） | ⚠ 部分（可校验文件编码为 UTF-8 无 BOM 异常） |
| `render/jobs.js` 变量重复声明（我引入的 bug） | ✅ `node --check` 全部 js |
| manifest 引用文件缺失 | ✅ 逐条 `Test-Path` |
| `.workbuddy/` 未排除会被打进 zip | ✅ 复用 `release.ps1` 的 `$excludePatterns` 做命中测试 |

建议内容（按执行顺序，全绿才允许发布）：
1. 全树无 `_` 前缀文件/目录
2. 所有 `*.js` 通过 `node --check`
3. `manifest.json` 合法 JSON，且 `content_scripts.js` / `background.service_worker` / `side_panel.default_path` 引用的文件全部存在
4. `sidepanel.html` 的 `<script src>` 全部存在
5. `manifest.json` 的 `version` 与 `release.ps1` 的 `$ver` 一致
6. `git ls-files` 的文件没有一条命中 `$excludePatterns`（防误打包）
7. 纯函数测试全通过（配合 3.3）

- **收益**：高。把"发布才发现"提前到"提交前发现"。
- **成本**：低到中，约 100 行 PowerShell。
- **风险**：无。

## 4. 附：可直接修的小而准问题清单

这些是我在通读中发现、**不属于架构层但真实影响正确性**的点，多数是 3~10 行可修。

### 4.1 判断题依赖字母映射，可能选反（正确性问题）

- **现状**：System Prompt 规定"判断题 answer 为 A（正确/对）或 B（错误/错）"（`ai.js:14`）；内容侧 `quiz.js:217` 把 `judge` 与 `single`/`multiple` 一并交给 `fillChoiceByIndex`，用 `getOptionLetter()`（`quiz.js:35`）从页面取字母后点击。
- **风险**：整条链路隐含一个**未经验证的假设 —— "页面的 A 就是『对』"**。`getOptionLetter` 优先读 `.num_option` 的 `data` 属性，读不到才按索引兜底为 A/B。若某页面把"错"排在前、或 `data` 标记与语义顺序不一致，AI 的 `A`（含义为"对"）就会被点到"错"上，**整题反向**。
- **改进：以"语义"为中间表示，而不是以"字母"为中间表示。**

  **数据流（三步，缺一步就会写错）**：

  ```
  ① 从页面选项文本反推每个字母的语义
       "A. 正确" → A 是 TRUE     "A. 错误" → A 是 FALSE
       "B. 错"   → B 是 FALSE    "B. 对"   → B 是 TRUE
       —— 这一步决定了映射来源是【页面】，而不是硬编码

  ② 把 AI 的答案转成规范语义
       "A" → TRUE      "B" → FALSE

  ③ 在①的映射里反查：语义为 TRUE 的是哪个字母 → 点击它
  ```

  **关键点：① 必须从页面文本推导，不能写成 `A → TRUE` 的硬编码表。** 若实现成硬编码，遇到页面顺序反过来（罕见但存在）会**整题反向** —— 那就等于把 bug 从一处搬到另一处。

- **语义归一表（用于①的文本识别，不是用于跳过①）**：

  ```
  {对, 正确, 是, true, √, T, Y, 是}      → TRUE
  {错, 错误, 否, false, ×, F, N, 不是}   → FALSE
  ```

  AI 说"正确/对"，页面可能写"对/正确/是/√/True"，所以**两边都要先归一再比对**；只用精确文本匹配会直接匹配失败。
- **兜底策略（重要）**：语义映射失败时（如页面选项既非对/错也非是/否，无法归类），**不要直接报错放弃**，而是**回退到字母通道 + 日志警告**。单路径失败 = "完全没填"，双路径最坏 = "可能填错但填上了"，后者对用户更可接受。
- **收益**：高（消除一类静默错误答案）；**成本**：约 25 行；**风险**：低（有兜底路径）。

### 4.2 多选题不会取消多余选中（正确性问题）

- **现状**：经复核确认 —— 字母模式下（`quiz.js:143-148`）只做"未选中则 click"，**从不取消已选项**：

  ```js
  letters.forEach((letter) => {
    const ab = letterMap.get(letter);
    if (!ab) return;
    if (isOptionSelected(ab)) { filled++; return; }   // 已选 → 跳过
    try { ab.click(); filled++; } catch (e) {}        // 未选 → 点击
  });
  ```

- **风险**：若页面上已有用户此前的选择、或上一轮填入的残留，最终选中集合是 **"正确答案 ∪ 残留选项"** 的超集 → 多选判错。
- **改进：把"点选"改为"先归一化选中集合，再按答案设置"。**

  **实现步骤（范围限定必须写进代码，不能只写在注释里）**：

  ```
  作用域 = 当前题目元素内的 .answerBg 集合     // 严禁扩大到整页
  目标集合 = 由答案推导出的「应选字母集合」

  第 1 步 清理：遍历 作用域 内所有已选项，
                 若其字母 ∉ 目标集合 → click 取消
  第 2 步 设置：遍历 目标集合，
                 未选中 → click；已选中 → 跳过
  ```

  **范围限定是硬要求**：若误写成"整页 `.answerBg` 全扫一遍"，会**清掉其他题**已有的选择，把一个小 bug 变成大事故。作用域必须自 `question.element` 向内取。
- **不应只改多选**：`single` / `judge` 也应走同一条"清理 + 设置"路径。
  - 原因：不能假设所有平台的单选都自动互斥。当前代码在单选上同样是"只点不清"，一旦页面残留了别的选项，结果不可预期。
  - 对单选/判断题，清理是**幂等且安全**的：目标集合只有一个元素，清理逻辑与多选完全一致，无需分支。
- **收益**：中高（消除一类静默错误答案）；**成本**：约 20 行（统一路径后反而比按类型分支更短）；**风险**：低（作用域限定 + 清理幂等）。

### 4.3 填入后不回读校验（可靠性问题）

- **现状**：`fillChoiceByIndex` 靠 `click()` 的返回值计数，`fillFill`（`quiz.js:186`）写完即 `return true`，都不验证页面的最终状态。
- **改进**：填入后统一走一次**回读校验**（对所有 `.answerBg` 调 `isOptionSelected`，与预期集合比对），不一致则在返回值里带上差异。这同时为 2.3 的复核 UI 提供数据。

### 4.4 `parseAnswers` 缺 index 校验（健壮性问题）

- **复核更正**：初稿称"越界 index 会静默落到错误的题上"，**这是说过头了**。实际内容侧是按 index 查找的（`main.js:480-489`）：

  ```js
  const q = questions.find(x => x.index === idx);
  if (!q) { console.warn(`[CXH] 找不到题目 index=${idx}`); failed++; continue; }
  ```

  越界 index 会被**拒绝并计入 failed**，不会错填。
- **真正的问题有两个**：
  1. **重复 index 无校验**。`ai.js:85-89` 直接采用 AI 返回的 `index`。若两条答案 index 相同，会**被同一道题连续填两次**，而另一道题无人处理 —— 且 `filled` 计数会把"重复填同一题"算作两次成功，**面板显示的完成度是虚高的**。
  2. **失败不可归因**。`FILL_QUIZ` 只回传 `filled` / `failed` 总数（`main.js:500`），面板无法告诉用户"第 3 题没填上"。用户看到"已填入 9/10"却不知道漏了哪题。
- **改进**：
  - `parseAnswers` 增加 `index ∈ [0, total)` 与**去重**校验，异常项丢弃并在日志中指名告警
  - `FILL_QUIZ` 的返回值增加 `failedIndexes: []`，供面板逐题标记（与 §2.3 的复核 UI 共用数据）

### 4.5 UEditor 写入未经编辑器 API（可靠性问题）

- 见报告 §6.3。改进为 `win.UE.getEditor(id).setContent()` + 回读。

### 4.6 验证码提交节奏过于机械（风控友好度）

- **现状**：识别 → 填入 → 提交 → 固定 2 秒 × 3 次检查（`captcha.js:328-338`），间隔完全固定。
- **改进**：在填入与提交之间、"检查"轮次之间引入小幅随机抖动（如 1500–2800ms）。完全等间隔的交互序列本身是可被识别的行为特征。
- **收益**：低到中；**成本**：极低（3 行）；**风险**：无。

### 4.7 日志与 Console 双写（性能与可测性）

- `modules/utils.js:36` 的 `U.log` 每条都强制 `console.log`。建议加开关，生产默认关闭 Console 输出（侧边栏 Console 长期开启会影响面板性能）。

### 4.8 API Key 明文存储（安全与隐私）

- **现状**：`modules/storage.js:5` 的 `mimoConfig`（含 `apiKey`）明文存于 `chrome.storage.local`，该区域**不加密**，同机其他进程可读。
- **改进**（三档，按侵入性递增）：
  - **方案 A（推荐）**：改用 `chrome.storage.session`（MV3 新增，纯内存态，扩展重载即清空）。代价是每次浏览器启动需重填。
  - **方案 B（折中）**：`chrome.storage.session` 存密钥 + `chrome.storage.local` 只存到期时间戳，实现"记住 24 小时"。
  - **方案 C（最小改动）**：保留现状，但在设置面板明示"密钥以明文保存在本机"。
- **顺带项**：验证码截图会上传整屏画面至第三方大模型（`captcha.js:93`）。**不建议改截图来源**（超星放大层的识别率显著优于原图，见分析报告 §6.7），但应在设置面板**显式告知**并给出开关。
- **收益**：中（隐私与知情权）；**成本**：约 30 行；**风险**：低。

### 4.9 清理遗留接口 `GET_CAPTCHA`

- **现状**：`main.js:389` 实现了 `GET_CAPTCHA`，但**面板侧全库无调用方** —— 它是 v0.5.0 改用 `captureVisibleTab` 截图方案后的遗留接口，处于"既不删除、也不作 fallback"的悬置状态。
- **改进**：**直接删除**。分析报告 §6.7 已论证它**不宜**作为截图 fallback（`<img>.src` 取到的是 40×20 像素级原图，识别率低于放大后的截图），保留只会让后来者误以为它是可用路径。
- **收益**：低（消除认知负担）；**成本**：删除约 12 行 + 文档同步；**风险**：无（无调用方）。

## 6. 一句话总结

当前项目在**"让视频真实播完"**这条主线上已经做得相当扎实（651 行的 player 子系统、四层并发控制、双重复查），真正的短板集中在三处：

1. **遇阻时只会停下来等人** —— 而超星的阻碍里有一大半是机器可判、可自动处理的（§1.1）
2. **过程不可见** —— 用户不知道还有多久、不知道是否需要自己动手、不知道自己填的答案对不对（§2.1–2.3）
3. **平台耦合没有隔离层** —— 超星改版一次就会伤筋动骨（§3.1、3.2）

这三点都不是"功能不够多"，而是**"已经能做的事没让人看见、没让人放心"**。补齐它们比新增功能更划算。
