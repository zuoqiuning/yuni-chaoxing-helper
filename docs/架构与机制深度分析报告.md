## 一、项目定位与本质判断

### 1.1 一句话定义

这是一个**基于 UI 自动化的学习通（超星）任务点推进器**：它不伪造任何进度上报请求，而是通过**驱动官方播放器以更高倍速真实播放 / 模拟真实用户滚动**，让平台自身的上报链路正常触发。

### 1.2 这一点决定了整个架构

从 `docs/学习通数据侦察脚本合集.md` 的「上报机制狩猎」脚本可以看出，开发者曾深入分析过超星的 `sendReadZTMediaLog`、`pwindow`、混淆函数字典等上报机制，但**最终没有走接口伪造路线**。全库检索确认：

- 没有任何 `XMLHttpRequest` / `fetch` / `sendBeacon` 的劫持或重放
- 唯一的 `fetch` 调用在 `background/background.js:117`，只用于调用小米 MiMo 大模型
- 所有"完成"状态都来自**平台自身**（`.ans-job-finished` class、`icon_Completed` 图标）

因此这是一个**"自动化操作 + 状态观测"**系统，而非**"协议逆向"**系统。这个选择带来了三个直接后果：

| 后果 | 表现 |
|---|---|
| 必须处理播放器状态机 | 倍速 Hook、暂停守护、节流心跳、卡死检测（`content/player/`） |
| 必须以 DOM 为唯一真值源 | 完成判定要做 4 层祖先链遍历（`jobs.js:11-43`） |
| 必须处理平台反自动化 | 验证码识别链路（`sidepanel/modules/captcha.js`） |

### 2.2 关键判定：单例与多标签页隔离

`manifest.json` 的 `content_scripts` **未声明 `all_frames`**，默认 `all_frames: false` —— 内容脚本**只注入顶层文档**。这是正确的设计决策：

- 顶层 `main.js` 的 `PING`（`main.js:354`）返回 `{ role: 'top' }`，sidepanel 的 `waitContentScript()` 依赖此判定
- 所有嵌套 iframe（`ananas/modules/video`、`ananas/modules/pdf`）的 DOM 访问，都通过**同源 `contentDocument`** 完成，而非再次注入
- 多标签页隔离靠 sidepanel 的 `SP.state.runningTabId` + `msg.sender.tab.id` 过滤实现

> ⚠ 一个被忽略的边界：`pan-yz.chaoxing.com` 与 `mooc1.chaoxing.com` **不同源**。`dom.getDocIframe()`（`dom.js:49`）会匹配到该 iframe，但 `doc.js` 中所有 `contentDocument` 访问都会被 `try/catch` 静默吞掉。详见 §6.2。

### 2.4 共享状态对象设计

两个全局状态容器是理解整个系统的钥匙：

```js

  stopped, paused, interrupted,        // 三种中断语义，含义严格区分
  currentVideoEl, currentVideoIframe,  // 当前视频句柄

  lastThrottleLogState, lastVideoTime, stuckTicks

// sidepanel/modules/utils.js:5 —— 面板域状态

  running, runningTabId, boundTabId, scanning,
  jobCards, jobCardsSectionId, localDoneJobs,
  playingCardIdx, playingJobIdx, playingJobId,

```

**`stopped` / `paused` / `interrupted` 三态语义**（全项目最容易混淆、也最关键的设计）：

- `stopped` —— 永久终止，`clearState()`（`section/index.js:348`）会置 `true`，所有循环都以此为退出条件
- `paused` —— 用户主动暂停，`waitIfPaused()`（`runner.js:11`）会阻塞任务流，`guard.js` 不介入恢复
- `interrupted` —— 一次性打断信号（用于 `requestRestart`），`waitEnded` 轮询检测到后**自动复位为 false**（`player/index.js:249-252`）

## 四、核心机制逐一剖析

### 4.1 目录扫描（`catalog.js`）

超星目录结构：`.posCatalog_select` 列表，章为 `firstLayer`，节 ID 藏在 DOM id 的 `cur` 前缀中。

```js
// catalog.js:10-15
if (node.classList.contains('firstLayer')) return;
const id = (node.id || '').replace(/^cur/, '');    // cur1198980960 → 1198980960
const finished = !!node.querySelector('.icon_Completed');   // ★ 完成态的权威来源
```

**关键设计**：`icon_Completed` 图标是**服务端返回的完成标记**，不依赖客户端状态。整个"断点续跑"体系的终点判据都是它（`section/core.js:51 isSectionFinished`）。

### 4.2 任务点识别与完成判定（`jobs.js`）

#### 4.2.1 四重 `judgeDone` 策略（`jobs.js:11-43`）

超星的完成标记会出现位置漂移，因此需要"由内向外、由近及远"逐层试错：


代码注释明确指出问题根源：**超星的 `aria-label` 与实际状态可能不一致**（`release.ps1` 的发行说明中也记录了这条修复）。因此 class 优先、aria 兜底，且都必须**沿祖先链向上 4 层**搜索。

#### 4.2.2 视频"实际播完但 DOM 未标记"兜底（近期改动）

位于 `section/index.js:51-64`，源码注释即为 `// ★★★ 改动 1`：

```js

    if (v && v.duration > 0 && !isNaN(v.duration) && v.currentTime >= v.duration - 2) {
```

**为什么必要**：服务端标记有延迟（视频播完 → 上报 → 服务端写库 → 目录图标更新），若只信 DOM，面板会长时间显示"未完成"，触发无意义的重复播放。

**归因说明**：v1 报告将此描述为"最巧妙的一处补丁"并归为作者原有设计，实为近期新增。技术上其价值成立，但它是**对上报延迟的被动补偿**，而非原始架构的一部分。

#### 4.2.4 卡片加载稳定性判定（`jobs.js:106-138`）

### 4.3 卡片（tab）切换同步：`num` 参数法

超星课程的一个"节"包含多张卡片（tab），每张卡片是一个独立 iframe 页面。切换卡片会重新加载 `#iframe`，其 `src` 携带 `num=N`（从 0 开始）。

**`dom.getIframeCardIdx()`（`dom.js:25`）从 URL 参数反解当前卡片索引**：

```js
const m = ifr.src.match(/[?&]num=(\d+)/);   // dom.js:29
```

这比"监听 tab 的 active class"更可靠 —— class 会立即变化，但 iframe 内容可能还在加载。`finder.waitForTabSwitch()`（`finder.js:65`）的逻辑是：

1. 轮询 `getIframeCardIdx() === targetIdx`（300ms 间隔）
2. 命中后调 `waitForCardLoaded(6000)` 等内容稳定，失败则再补等 1500ms
3. **二次确认** iframe 仍指向 target（第 80 行，防止切换过程中被平台改写）

**`scanCardNow` 的自校验**（`section/index.js:43-46`）：若 `getIframeCardIdx() !== cardIdx`，返回 `{_skip:true}` 让调用方跳过 —— 避免"tab 高亮已切换但 iframe 未跟上"导致的**张冠李戴**。

### 4.4 视频播放引擎（`content/player/`，651 行，全项目最复杂子系统）

这是整个扩展的技术核心。视频必须**真实播放到最后 1 秒**，因此需要对抗四类故障。

#### 4.4.1 五类故障与对应防御

| 故障 | 成因 | 防御机制 | 位置 |
|---|---|---|---|
| 元数据未就绪就 `play()` | 源未加载 | `smartPreload` 三段式加载 | `core.js:126` |
| 自动播放策略拦截 | 无用户手势 | `safePlay` 静音降级 + 500ms 后恢复音量 | `core.js:191`（降级分支 211-226） |
| 平台主动暂停 | 防挂机检测 | `hookPauseGuard` pause 监听 | `guard.js:9`（监听 15） |
| 浏览器节流 | 标签页后台 8s+ | 心跳 gap 检测 | `guard.js:56`（判据 64） |
| 倍速被重置 | 平台周期性覆写 | `installRateHook` 双保险 | `core.js:30` |

#### 4.4.2 `smartPreload` 的加载策略树（`core.js:126-170`）

```
video.error? ──是──▶ 失败                                    (127-130)
duration 已就绪? ──是──▶ 成功                                 (131)
10s 内 currentSrc/src 出现? ──否──▶ 失败                      (133-139)
读取 networkState:                                            (145-155)
   ├─ 3 (NO_SOURCE) ──▶ resetSrc()
   ├─ 0/1 (EMPTY/IDLE) ──▶ player.load() 或 video.load()
   └─ 2 (LOADING) ──▶ 直接等待
waitMetadata(20000) ──成功──▶ 成功                            (156)
     │失败
resetSrc() + waitMetadata(15000) ──▶ 成功 / 失败               (163-168)
```

`resetSrc()`（`core.js:77`）是一个值得注意的技巧：它**备份 `video.src` 与所有 `<source>` 子元素、全部移除、`load()` 清空、再原样回填并 `load()`**，用于强制播放器重新走一次资源协商，规避 `NO_SOURCE` 死锁。

#### 4.4.3 倍速 Hook 的双保险（`core.js:30-39`）

```js
// 保险 1：事件驱动
v.addEventListener('ratechange', () => setTimeout(() => applyRate(v, pl, rate), 0));   // 33
// 保险 2：轮询驱动
const intervalId = setInterval(() => {
  if (!v.isConnected) { clearInterval(intervalId); return; }   // ★ 自清理，防泄漏 (35)
  if (!v.paused && v.playbackRate !== rate) applyRate(v, pl, rate);
}, 1000);                                                       // 37
```

`applyRate`（`core.js:23`）**同时**写 videojs player（`player.playbackRate(rate)`）与原生 `video.playbackRate` —— 因为超星用 videojs 封装，两者可能不同步。

#### 4.4.4 三层守护（`guard.js`）

**层 1：`pause` 事件兜底**（`guard.js:15-36`）
1500ms 去抖（第 22 行），400ms 延迟后复查全部条件才静音续播（第 25-35 行）：

```js

if (P.stopped || P.paused || P.interrupted) return;   // 尊重中断语义
if (v.ended || v.error) return;
if (!v.isConnected) return;
if (!core.canSafelyRecover(v)) return;        // 六项安全校验

```

另附 `visibilitychange` 简版恢复（`guard.js:46`，注释标记 `★ 修复隐患 3`）。

**层 2：节流心跳**（`guard.js:56-78`，3s 间隔）
测量 `setInterval` 实际间隔，`gap > 8000`（第 64 行）即判定标签页被浏览器节流 —— 这是对"后台标签页定时器被降频"的直接探测，比监听 `visibilitychange` 更鲁棒（后者无法覆盖"窗口可见但被降频"）。

**层 3：卡死检测**（`guard.js:80-102`，2s 间隔）
`currentTime` 连续 3 次（第 89 行，约 6 秒）变化 <0.3 秒 → 判定卡死 → 强制静音续播。

**`canSafelyRecover()`（`core.js:41-49`）是三层守护的统一准入闸门**：

```js
v.isConnected && !v.error && !v.ended && (v.currentSrc || v.src)
  && v.readyState >= 2 && v.duration > 0
```

#### 4.4.5 `waitEnded`：终局等待的状态机（`player/index.js:224-286`）

3 秒轮询（第 283 行），七种分支：

| 行号 | 条件 | 动作 |
|---|---|---|
| 249 | `P.interrupted` | **复位标志**，返回 `{error:'interrupted'}` |
| 254 | `P.stopped` | `v.pause()`，返回 `{error:'stopped'}` |
| 259 | `P.paused` | 计数清零，跳过本轮（保持暂停） |
| 260 | `v.error` | 返回错误 |
| 264 | `ended \|\| currentTime >= duration - 0.5` | **成功** |
| 268 | `detectBlockers()` 命中 | `v.pause()`，返回 `{error:'blocked: ...'}` |
| 274 | `v.paused && currentTime < duration - 1` | `pausedCount++`，≥3（第 276 行）→ `safePlay(v,true)` |

超时设置 **3,600,000 ms（1 小时）**，见 `runner.js:114`，为超长视频留余量。

`detectBlockers()`（`core.js:172-189`）探测五类遮挡层（第 175-178 行）：

命中后不是硬试，而是**暂停 + 上报 `BLOCKED`**（`runner.js:128`）交由用户处理。

#### 4.4.6 `forceResume`：最后的核弹（`player/index.js:95-178`）

当常规恢复全部失败（video 元素已从 DOM 卸载、播放器实例失效）时触发：

```

  ↓ 最多 15 秒（MAX_WAIT，第 112 行），每 500ms 轮询
```

第 124-128 行的 `restartFlag` 检查带有 `★★★ 改动 2` 标记（近期补入）。

#### 4.4.7 节漂移检测（`finder.js:115-150`）

在 `waitEnded` 之上再包一层 2 秒轮询（第 123 行）：一旦 `isOnSection()`（第 119-122 行）判定节已切换，立刻 `v.pause()` 并返回 `{sectionChanged:true}`。

### 4.5 文档任务：滚动模拟（`doc.js`）—— 全项目最弱的一环

超星的文档/PDF 阅读进度依赖**滚动事件触发懒加载与上报**，因此策略是"尽可能制造滚动"。


## 六、问题清单与改进建议

按严重程度排序，每条给出**定位、成因、影响、建议**。

### 6.1 【高】文档任务"乐观成功"，可能被永久跳过

- **定位**：`content/doc.js:208`（末尾无条件 `return { ok: true }`）→ `content/section/runner.js:67` → `content/section/index.js:163`
- **成因**：无论滚动是否触发上报、iframe 是否可访问，都返回成功
- **影响**：文档任务被标记完成并写入 30 分钟 TTL 的进度缓存，期间不会被重试；面板显示"已完成"但目录仍为未完成，体验割裂
- **建议**：在返回前调用 `checkAttachDone(attach)`（`doc.js:131` 已实现），未命中则返回 `{ok:false, error:'not confirmed'}`；跨域场景显式返回 `{ok:false, error:'cross-origin'}` 并降级为"提示用户手动打开"

### 6.2 【高】跨子域 iframe 静默失效

- **定位**：`content/dom.js:49-59`（`getDocIframe` 正则匹配 `pan-yz.chaoxing.com`，且第 55-57 行有"取首个非 about:blank iframe"的兜底）；`content/doc.js:147-154`（同样的兜底在第 154 行）；`content/doc.js:14-23`（`collectFrames` 的 `try/catch` 吞掉全部异常）
- **成因**：`mooc1.chaoxing.com` 与 `pan-yz.chaoxing.com` 不同源，`iframe.contentDocument` 抛 `SecurityError` 后被静默捕获
- **影响**：该类型文档任务 100% 假成功；且兜底分支可能**把不可访问的跨域 iframe 当作文档容器**，掩盖"根本没找到正确容器"这一事实。用户无法从日志感知
- **建议**：`collectFrames` 的 catch 中补 `utils.log('  跨域 frame 跳过: ' + src, 'err')`；`getDocIframe` 与 `doc.js:154` 的兜底分支移除或限制为同源

### 6.3 【中】`quiz.submit()` 未接线 + UEditor 写入不完整

- **定位**：`content/quiz.js:234-238`（`submit` 定义，未出现在 `main.js:351` 任何 case）；`content/quiz.js:190-204`（UEditor 路径）
- **成因**：`submit()` 是死代码；UEditor 只改 `iframe.contentDocument.body.innerHTML`，未调用 `UE.getEditor().setContent()`
- **影响**：填空/简答内容可能在编辑器失焦时被内部状态覆盖
- **建议**：若刻意不提交（当前设计语义明确），删除 `submit()` 以消除歧义；UEditor 路径优先通过 `win.UE.getEditor(id).setContent()` 写入

### 6.4 【中】`LOG` 消息在空闲态不隔离

- **定位**：`sidepanel.js:197-200`
- **成因**：过滤条件依赖 `SP.state.runningTabId` 非空
- **影响**：未运行任务时，任意学习通标签页的日志（含验证码检测、卡片扫描日志）混入同一面板
- **建议**：改用已存在的 `SP.state.boundTabId` 作为过滤键（`boundTabId || runningTabId`），并对日志行加来源标签

### 6.5 【中】`jobCardsSectionId` 初始化缺失导致本地完成态 key 错位

- **定位**：`sidepanel/modules/render/jobs.js:132`（`renderCardJobs` 未设置 `jobCardsSectionId`）、`jobs.js:26-28`（`_sKey` 兜底 `'default'`）
- **成因**：首次 `CARD_JOBS`（`sidepanel.js:217`）渲染时 `jobCardsSectionId` 为 `null`，`_sKey` 落到 `'default'`；随后 `CARD_JOBS_UPDATE`（224）携带 `sectionId` 会切换 key
- **影响**：`localDoneJobs` 中同一记录可能挂在两个 key 下，极端情况下 UI 出现"刚标记完成又变回未完成"（content 侧 `done` 仍为准，影响有限）
- **建议**：`renderCardJobs(cards, sectionId)` 增加第二参数并赋值，或在 `CARD_JOBS` 分支先写 `SP.state.jobCardsSectionId = msg.sectionId`

### 6.6 【中】节漂移判定口径不一致

- **定位**：`content/section/finder.js:119-122`（仅 `chapterId`，经 `dom.getCurrentSectionId()`，实现见 `dom.js:79-82`）vs `content/main.js:34`（`chapterId` ∨ `#curChapterId` ∨ `knowledgeid`）
- **成因**：`dom.getCurrentSectionId()` 只读 URL 的 `chapterId`；部分课程由 iframe 的 `knowledgeid` 驱动，URL 参数不变
- **影响**：`waitEndedWithSectionCheck` 可能把正常播放误判为"节被切换"，导致视频被暂停、`processOneSection` 触发 `ensureOnSection`（`task.js:25`）反复切回
- **建议**：把 `main.js:34` 的三通道判定下沉为 `dom.isOnSection(sectionId)`，`finder.js` 复用

### 6.7 【中】验证码截图范围过大 + 密钥明文存储

- **定位**：`sidepanel/modules/captcha.js:93`（`captureVisibleTab` 截取**整个可见窗口**）、`sidepanel/modules/storage.js:5`（`mimoConfig` 明文存 `chrome.storage.local`）
- **成因**：`captureVisibleTab` 无区域裁剪能力；`chrome.storage.local` 本身不加密
- **影响**：窗口内其他内容（邮件、聊天、文档）随截图上传至第三方大模型；API Key 可被同机其他进程读取
- **建议（截图）—— 隐私与识别率的权衡，不可一边倒**：
  - **保留全屏截图作为主路径。** 超星检测到验证码时会弹出**放大层**，`captureVisibleTab` 恰好拿到的是**放大后的清晰图**；而 `GET_CAPTCHA` 走 `<img>.src` 取到的是原始小图（40×20 像素级），大模型对低分辨率手写字母的识别率会显著下降。**因此"改用 `GET_CAPTCHA`"是错的建议 —— 不能用识别准确率换隐私。**
  - **隐私问题改用"显式告知"解决**：在设置面板明示"验证码截图（含当前窗口画面）会上传至第三方大模型"，并提供开关。
  - **可选增强**：调用前检测窗口内是否有其他标签/敏感区域并提示用户；或提供"仅在识别失败时才截图"的降级策略。
  - **不推荐**：双路径各跑一次取高置信度 —— 请求数翻倍、延迟翻倍，而两条路径的输入质量并不等价（放大层优于原图），收益不确定。
- **建议（密钥存储）**：
  - **方案 A（推荐）**：改用 `chrome.storage.session`（MV3 新增，纯内存态，扩展重载即清空）。代价是每次浏览器启动需重填
  - **方案 B（折中）**：`chrome.storage.session` 存密钥 + `chrome.storage.local` 存到期时间戳，实现"记住 24 小时"
  - **方案 C（最小改动）**：保留现状但在设置面板明示"密钥以明文保存在本机"

### 6.8 【低】重复实现导致的认知漂移风险

## 七、设计亮点总结

撇开合规争议，从纯工程角度看，这个项目有若干值得借鉴的设计：

1. **"以平台自身为真值源"的克制** —— 没有去伪造上报，避免了与平台协议强耦合的维护地狱，代价是必须处理播放器状态机，作者选择承担后者。
2. **`num` 参数反解卡片索引**（`dom.js:25-33`）—— 用 URL 参数而非 DOM class 判断异步切换状态，是异步 UI 同步的经典手法。
3. **签名稳定性判定**（`jobs.js:122-138`、`doc.js:190-196`）—— 用"结构签名连续 N 次不变"替代"固定 sleep"，兼顾速度与稳健。
4. **`globalRunId` + `pendingResume` 双保险**（`task.js:12`、`captcha.js:177`）—— 长生命周期异步流程的并发控制范本。
5. **`sessionStorage` 跨刷新存活**被用作断点续跑的持久层 —— 巧妙利用了浏览器语义（标签页内跨 reload 保留、跨标签隔离），与"多课程页互不干扰"的需求天然契合。
6. **`gap > 8000` 的节流探测**（`guard.js:64`）—— 通过测量定时器实际间隔感知浏览器节流，比监听 `visibilitychange` 更鲁棒。
7. **噪声词表驱动的 LLM 输出解析**（`ai.js:189-218`）—— 34 词黑名单 + 大小写混合度打分，是"让 LLM 稳定输出结构化结果"的实用工程手段。
8. **`canSafelyRecover` 统一准入闸门**（`core.js:41-49`）—— 所有恢复路径共用同一组六项安全校验，消除了大量分散的边界判断。
9. **`★★★`/`★` 增量变更标记约定** —— 在注释中标记近期修改点（`jobs.js:9`、`doc.js:130/169/178`、`core.js:8`、`section/index.js:51`、`player/index.js:124`、`guard.js:45`、`status.js:7` 等），使"哪些是基线、哪些是新补丁"在阅读时一目了然。这是 v1 报告遗漏的信号，实际显著提升了本次分析的可追溯性。

## 八、数据侦察脚本的价值定位

`docs/学习通数据侦察脚本合集.md`（1,101 行）是一套**只读控制台脚本**，记录了作者的逆向过程：

| 脚本 | 目的 | 输出 |
|---|---|---|
| 一键全量侦察 | 课程结构 / 目录 / 任务点 / iframe / 全局函数 / 隐藏 input / storage / cookies | `window.__reconData` |
| 卡片扫描 | 遍历全部卡片收集任务点 | `window.__allCards` |
| 视频 iframe 深度侦察 | 钻进 video iframe，Hook XHR/fetch/sendBeacon，dump videojs player | `window.__videoRecon2` |
| 上报机制狩猎 | 播放 60 秒捕获全部上报请求、统计间隔、dump `pwindow`、还原混淆函数字典 | `window.__reportHunter` |

**关键情报**（记录在脚本的"数据解读"章节，也是当前实现的原型依据）：

- `videoAutoPlay = "0"` —— 官方自动播放默认关闭，必须手动 `play()` → 解释为何需要 `safePlay`（`core.js:191`）与静音降级
- 隐藏 input `_studystate = {nextChapterId, unfinishCount}` —— 全局进度
- `taskPoints[].jobId` / `objectId` —— 上报接口的标识字段 → 对应 `jobKey` 的降级链（`section/core.js:44`）
- `metadata timeout` —— `readyState=0` 时调 `play()` 的典型错误 → 对应 `smartPreload` 的三段式加载（`core.js:126`）
- 任务点 `done=true` 但平台仍要求重播 —— DOM 状态滞后 → 对应"以服务端 `icon_Completed` 为准"的设计原则（`catalog.js:15`）

这些脚本本身**不提交任何进度、不点击提交按钮、不修改状态**，与扩展的运行时代码完全解耦（扩展不加载它们）。

> **快照一致性说明**：作者的 `项目代码.md` 导出**排除了 `docs/` 目录**（导出时的树形结构显示 `docs/` 为空），而本报告引用的 `docs/学习通数据侦察脚本合集.md`（1,101 行）确实存在于工作区。二者基于不同快照，统计数字（§0.2）不含该文档。

## 九、总体评价

| 维度 | 评价 |
|---|---|
| 架构清晰度 | **良好**。三上下文职责分明，content 侧 15 个文件的依赖顺序被 `manifest.json` 精确编排，命名空间 `__CXH` / `SP` 无污染。 |
| 异常处理密度 | **高**。几乎每个 DOM 访问都被 `try/catch` 包裹，`waitFor` 有超时，`sendToTab` 有 `Promise.race` 兜底。代价是可观测性下降（异常被吞，见 §6.2）。 |
| 并发控制 | **优秀**。`globalRunId` / `pendingResume` / `restartFlag` / `stopped-paused-interrupted` 四套语义互补，覆盖了长流程的所有中断场景。 |
| 状态一致性 | **良好**。三层进度载体职责明确，服务端为唯一权威判据。 |
| 幂等与重试 | **良好**。节级 3 次、pass 级 2 次、全局 5 轮、最终补救 2 轮，多层收敛。 |
| 安全性 | **偏弱**。API Key 明文存储、全屏截图外传、`<all_urls>` 权限过宽。 |
| 代码整洁度 | **中等**。存在 4 处重复实现、4 处死代码/悬置接口；`main.js`（507 行）与 `sidepanel.js`（398 行）职责偏重，可拆分。 |
| 可维护性 | **中等偏上**。注释密度高且带 `★★★` 变更标记（本项目的独特优势）；但 `release.ps1` 内嵌约 80 行发版说明、`项目代码.md` 快照双份维护，增加了同步成本。 |

**一句话结论**：这是一个在"不伪造协议"的自我约束下，把 **UI 自动化做到了工程可接受上限**的项目 —— 它的复杂度几乎全部来自"要让真实播放完成"这一条约束；而它最脆弱的地方，恰恰是唯一无法用 DOM 自动化保证的环节：**文档滚动与跨域 iframe**。
